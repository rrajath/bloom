# Architecture

Bloom is a single-module Android app (`:app`) organized into layered packages, plus a test-only `:macrobenchmark` module that ships nothing. The layers are held together by three invariants; almost every design choice in the codebase traces back to one of them:

1. **Files are the source of truth.** The `.org` files in the user's chosen folder are the only durable state. Anything Bloom stores elsewhere (the Room index, parse caches) must be derivable from the files by re-reading them.
2. **Parsing is lossless.** An `OrgDocument` is a *view over* the raw text, not a replacement for it. Serializing a parsed document returns the original text unchanged. Edits are text splices, never re-renders of a model.
3. **External tools may touch the files at any time.** Syncthing, Emacs over SSH, a file manager: Bloom detects changes by revision and never assumes it is the only writer.

## Layer map

```
┌──────────────────────────────────────────────────────────────┐
│ ui/            Compose screens · ViewModels · theme          │
│                (StateFlow in, user intents out)              │
├──────────────┬──────────────┬──────────────┬─────────────────┤
│ capture/     │ search/      │ sync/        │ settings/       │
│ templates,   │ query parse, │ engine,      │ DataStore       │
│ placeholders,│ match, rank, │ triggers,    │ preferences     │
│ insertion    │ snippets     │ conflicts    │                 │
├──────────────┴──────────────┼──────────────┴─────────────────┤
│ org/                        │ data/                          │
│ parser · mutations ·        │ Room index: a rebuildable      │
│ timestamps · line editing   │ cache over the vault           │
├─────────────────────────────┴────────────────────────────────┤
│ vault/    Vault facade → FileStore (SafFileStore | JvmFileStore)
└──────────────────────────────────────────────────────────────┘
```

Dependencies point downward only. `org/`, `capture/`, `search/`, and the `SyncEngine` are pure Kotlin with no Android imports, which is what makes the ~150-test JVM unit suite possible.

## The org engine (`org/`)

`OrgParser.parse(text)` produces an `OrgDocument`:

- `text` and `lines`: the verbatim file content. `serialize()` simply returns `text`.
- `headlines`: a flat, document-ordered list of `OrgHeadline` values. Each headline records its `lineIndex`, `level` (star count), parsed keyword/priority/title/tags, planning timestamps, any bare active `<date>` timestamps in its own body (`activeTimestamps`, including inline-in-prose ones; `dedicatedActiveTimestamps` is the subset on a dedicated first body line, which the tabbed dates editor manages), properties drawer contents, and the line ranges of its own body (`bodyStart`..`contentEnd`).

Tree structure (children, subtrees, parents, inherited tags) is *computed* from the flat list by comparing levels, not stored. This keeps the model trivially consistent with the text.

All edits go through `OrgMutations` (move/delete/cut/paste subtrees, set keyword/priority/tags/planning, mark done with repeater advancement) or `CaptureInserter`. Both work the same way: compute a line range from the parsed view, splice new lines into the raw text, and re-parse. Lines outside the splice are preserved byte-for-byte.

Supporting pieces: `OrgTimestamp` (parse/format org timestamps incl. repeaters and native `<a>--<b>` ranges via `rangeEnd`; `parseAll` pulls every stamp out of a block of text), `OrgKeywords` (configurable TODO/DONE keyword sets, `"TODO IN-PROGRESS | DONE CANCELLED"` syntax), `InlineTokenizer` and `BlockParser` (inline markup and block structure for rendering), and `LineEditing` (pure cursor-aware helpers for list continuation, heading demotion, and new-note caret placement, shared by both editors).

## The vault (`vault/`)

`FileStore` is a small suspend interface (`list / listDir / read / write / create / rename / delete / exists / pruneEmptyDirs`) over a **tree** of files. Every path is vault-relative with `/` separators (`projects/clients/acme.org`); a root-level file's path is just its name. Two implementations:

- `SafFileStore`: production. Wraps a persisted Storage Access Framework tree URI. `list` walks every subdirectory breadth-first (one child-documents cursor query per directory), skipping dot-directories and Syncthing's `.stversions`/`.stfolder`; warm path→doc-id caches (files and directories) keep repeat resolves cheap. `listDir` answers for a single folder (Dailies) without the full walk: it resolves the folder segment by segment from the nearest cached ancestor, runs one children query, and warms the file-id cache so the follow-up `stat`/`read` doesn't walk either. Before the first walk, a lookup of one uncached name on the local-storage provider (path-shaped document ids, `<volume>:<path>`) is a single direct document query rather than a walk; other providers still fall back to `list`. `create` walks and creates any missing intermediate directories; `rename` splits a same-directory rename from a cross-directory move (`DocumentsContract.moveDocument`, with a copy+delete fallback for providers that refuse it). Writes use mode `"wt"` (write+truncate; plain `"w"` does not truncate on all providers); document-provider quirks (name mangling on create, providers that throw from rename/delete) are absorbed here.
- `JvmFileStore`: plain `java.io` (`walkTopDown`, `mkdirs` on create/rename), used by unit tests and reusable for a future direct-filesystem location.

`pruneEmptyDirs(dir)` removes `dir` and any now-empty ancestor directories (stopping at the first non-empty one, never touching the vault root), collapsing empty descendant subdirectories first. `Vault` calls it after a delete or folder move empties a directory.

`Vault` is the facade the rest of the app uses: it lists notebooks recursively (filtering non-`.org` files, Syncthing conflict copies, and `.orgzlyignore` matches), opens files as parsed `OrgDocument`s with an `(name, mtime, size)`-keyed parse cache, and implements create (into any directory, creating missing folders), rename, `moveNotebook` (relocate keeping the file name), `renameFolder` / `deleteFolder` (rename or delete a whole directory by moving/deleting every descendant `.org` file, then pruning the emptied folder), save, and delete. "Delete" is **permanent** — SAF exposes no OS-level trash, so `deleteNotebook` / `deleteFolder` remove the file(s) outright via `DocumentsContract.deleteDocument` and prune the emptied directory. Recovery relies on the sync backend's own history (Syncthing file versioning).

A notebook's **identity** is its vault-relative path — the key everywhere: the Room index (`fileName`), `notebookColors` / favorites / the pin list, and every nav route and deep link (`Routes.encode` percent-encodes `/` to `%2F`). Since a root-level file's path equals its bare name, keys for files that predate nested folders stay valid; only nested files introduce new keys. A **folder's** identity is its vault-relative directory path: `folderColors` in settings is keyed by it, and `SettingsRepository.renameFolderStyle` / `deleteFolderStyle` re-key or drop those entries (plus every descendant file's) alongside the `Vault` file moves.

Pinned notebooks and folders share **one ordered list**, `GroveSettings.pinnedItems` (DataStore key `pinned_items`): `;`-joined `<tag><path>` tokens where the tag is `f` (file) or `d` (folder). List order is the Notebooks screen's Pinned-strip order (append on pin, remove on unpin), so a folder pinned after a file stays below it. `pinnedNotebooks` / `pinnedFolders` remain as derived filtered accessors. A pinned folder is lifted out of the inline tree entirely (its whole subtree with it) and shown only in the strip; `pinnedFolderSubtreeRows` re-flattens one pinned folder's contents, depth-shifted, so the strip row can expand in place, while a pinned folder over the drill threshold still opens the full-screen drill view on tap. The two older per-type keys (`pinned_notebooks`, `pinned_folders`) are folded into the unified list on first read (folders then files, matching the old strip order) and purged on the next write; settings import also reads them from an older export. The unified list travels with settings import/export.

The `flatten_notebook_folders` setting (Settings → Look and Feel) swaps the inline tree for a single flat list: `NotebooksViewModel` takes a dedicated state branch that fills `flatRows` / `flatPinned` from `NotebookTree.flatNotebookRows` / `flatPinnedRows` (pure, path-grouped; a pinned folder expands to its files inline, de-duped against nested pins) instead of `rows` / `pinnedStrip`, and `NotebooksScreen` renders every entry as a `FileRow(flat = true, showPathSubtitle = true)` — no folder rows, drill view, or expand/collapse-all. It's a view toggle only: folder identity, moves, and the pin list are unchanged.

A file's **revision** is the string `"mtime:size"`: cheap to compute from a directory listing and good enough to detect external edits.

## Sync (`sync/` + `data/`)

For the v1 local-folder backend, "sync" means **re-indexing**: the files are already the truth (Syncthing moves the bytes), so Bloom's job is noticing changes and keeping its index current.

- `SyncEngine` is the pure state machine: `Idle → Checking → Pulling → Done/Error`. It diffs current revisions against the index's known revisions, re-reads changed files into the index, removes vanished ones, and detects Syncthing `.sync-conflict-*` copies. It talks only to the `FileStore` and `NoteIndex` interfaces, so it is fully unit-tested; v2 remote backends (WebDAV/Dropbox) will implement `FileStore` against a remote and add an upload leg (the `Merging`/`Pushing` states exist for them).
- `RoomNoteIndex` implements `NoteIndex` over Room: each notebook file becomes a `NotebookEntity` (revision, top-level note count, conflict marker, cached `#+TITLE:`, and any file-level `:ID:` for whole-file links) plus one `NoteEntity` per headline (title, keyword, tags, inherited tags, planning timestamps, bare active timestamps as a space-joined `activeTimestamps` column (schema v12, destructive-migrated like every other version), IDs, full body text for search) and a mirrored row in the `notes_fts` FTS5 table. All of that happens inside one `@Transaction` per file, so the FTS mirror can never drift from the rows it indexes. The database is **never trusted as state**: it has destructive migrations and a "wipe and rebuild on next sync" recovery path by design.
- `SyncManager` is the Android-side orchestration: serializes runs behind a mutex, wires triggers (manual button, app foreground/background via `ProcessLifecycleOwner`, periodic `WorkManager` job ≥15 min, continuous 10 s polling while foregrounded), keeps a sync log in Room, posts conflict notifications, and implements conflict resolution (keep current / keep conflict copy / keep both; "both" demotes the conflict copy's content under a `* CONFLICT` heading).
  - **Trigger coalescing** (`SyncCoalescer`): every `requestSync` goes through one `Channel(CONFLATED)` with a single consumer, so a burst of triggers arriving close together (a save next to a poll tick, foreground + poll-start in one frame) collapses into one full pass instead of running back to back; a 200 ms debounce lets an idle-time burst settle first. `requestReindex` (single-file save path) and `clearAndResync` (keyword-change wipe) keep their own paths but still share the mutex.
  - **Continuous-poll change detection**: the 10 s poll fingerprints the directory listing (`directoryFingerprint`, FNV-1a over each file's name/mtime/size) and only calls `requestSync` when the fingerprint moves, so an unchanged vault costs one cheap SAF listing per tick and nothing else.

## Capture (`capture/`)

A `CaptureTemplate` is `(name, icon, target file, target location, template text)`, persisted as JSON in DataStore; built-in defaults are seeded until the user first saves. The target file is a vault-relative path (`FilenameValidation` accepts `/`-separated segments, not just a bare name), so a template can capture into a notebook in a subfolder; a missing target file (and its parent folders) is created on first capture.

The pipeline at capture time:

1. `PlaceholderExpander.prompts()` finds `%^{prompt}` placeholders; the UI collects answers first.
2. `PlaceholderExpander.expand()` substitutes placeholders (`%t %T %u %U %date %time %day %year %month %clipboard %shared_text %shared_url` …) and records where `%cursor`/`%?` puts the caret. For date-granularity targets (datetree by date), `%U`/`%u` expand date-only.
3. `CaptureInserter.withHeadingStars()` prefixes the entry with the heading stars it will receive on insert (4 for a datetree entry, 1 for top/bottom of file) so the editor is WYSIWYG.
4. On save, `CaptureInserter.insert()` splices the entry into the target file: at top/bottom, under a heading found by `ID` (falling back to `CUSTOM_ID`, so legacy templates resolve) or exact title (as a child heading, or, for a body-only template whose first line isn't a heading, verbatim into that heading's own body), or into a `year → month → day` datetree whose nodes are created on demand in chronological position. The first line is re-leveled to the insertion depth; body lines are kept verbatim.

Capture is reachable from the notebook-list FAB, a Glance home-screen widget, the share sheet (first URL → `%shared_url`, the rest → `%shared_text`), an optional ongoing notification, and the `bloom://capture` deep link.

## Search (`search/`)

`QueryParser` parses the Orgzly-compatible syntax (see [search-syntax.md](search-syntax.md)) with a small recursive-descent parser into a `SearchQuery`. Brackets nest, so the parser first builds an `Expr` tree (`And`/`Or`/`Leaf`) and pushes `.( … )` negation down to the terms (De Morgan), then flattens it to disjunctive normal form: `groups`, an OR-list of AND-groups of `Condition`s, plus sort and agenda directives. `QueryMatcher` decides matches off the tree; everything downstream that needs per-group structure (FTS/SQL narrowing, snippet selection, file-name matching) reads the flat `groups` unchanged. Flattening multiplies out each AND of ORs, so past `QueryParser.MAX_GROUPS` (64) the flat form is left empty: the tree still decides every match, narrowing falls back to the full scan, and results show as headings without text snippets. Date tokens follow Orgzly: a token without an operator takes its prefix's default (`le` for `s.`/`d.`/`cr.`, `eq` for `c.`/`e.`), and offsets always count from today. Settings that change a query's meaning (keyword order for `o.st`, default priority for `p.`) reach `QueryMatcher` as `MatchOptions`. Saved searches carry a syntax version in the `search` DataStore; ones written before the Orgzly date defaults are rewritten on read by `QueryMigration` so they keep their meaning. `QueryMatcher` evaluates conditions against indexed `NoteEntity` rows; `Snippets` produces highlighted excerpts. An `ad.N` query swaps Search's by-notebook layout for day sections: `SearchAgenda` (`ui/search/`, pure, JVM-tested) places each match on its days, reusing `AgendaBuckets`' placement rule and day labels, and `SearchUiState.days` carries the result (null for every other query). Search result rows share Agenda's swipe-to-commit row with second cells: the left side is [Done | State] on an open task (a long swipe marks it done via `SearchViewModel.markDone`, the same `AutoArchive` path as the state picker), the right side [Schedule | Reveal], where Reveal opens `Routes.outline(…, reveal = line)`; the Outline then unfolds the heading's ancestors, scrolls to it and fades an `accentSoft` wash off it once per back-stack entry.

**Matching is still decided in Kotlin; SQLite only narrows the candidates.** `FtsQuery` turns a parsed query's text terms into an FTS5 `MATCH` expression and `NoteCandidateQuery` turns its facets (`i.`/`p.`/`t.`/`b.`, and the Filters panel's chips) into a SQL `WHERE`. Both are built to return a **superset** of the real results, never a subset, so `QueryMatcher` and `matchesFilters` produce byte-identical output to scanning the whole vault. Anything that cannot be guaranteed a superset is simply not pushed down: terms shorter than a trigram, negated terms, date-window arithmetic over org timestamp strings, and non-ASCII operands (SQLite's `NOCASE`/`LIKE` fold only ASCII, Kotlin's `ignoreCase` folds all of Unicode). If *any* AND-group of a query has no usable text term, narrowing is abandoned for that query and the full scan runs: a facet-only group can match rows containing none of the query's text, so narrowing there would drop valid results. `FtsParityTest` pins this equivalence for every query shape.

Because the FTS5 module is absent from Android's platform SQLite (which is why Room only offers `@Fts3`/`@Fts4`), the database runs on `BundledSQLiteDriver` from `androidx.sqlite:sqlite-bundled`. The `notes_fts` virtual table is created by hand in a `RoomDatabase.Callback` and read through `@RawQuery`; if creation ever fails, `IndexDao.ftsAvailable` stays false and everything degrades to the full scan rather than breaking. Because `notes_fts.fileName` is `UNINDEXED`, a per-file `DELETE … WHERE fileName = ?` would scan the whole content table; the Room-owned `notes_fts_map` (`fileName`, `lineIndex` → the rowid SQLite assigned each mirror row) lets the per-file delete target rowids instead. It is written in the same `@Transaction` as the mirror and rebuilt destructively alongside it on a schema bump.

`FilenameMatcher` is an additive pass layered on top of this, not part of it: it matches a query's plain-text terms against notebook file names / vault-relative paths straight off the `NoteFacetRow` projection the view model already holds, with no query and no effect on `QueryMatcher` or the FTS parity guarantee. A file whose name matches floats above every content-only group (ranked exact base name > prefix > substring, then `lastModified`) and gets a synthetic `FileMatchRow` that opens its outline, even when nothing inside it matched.

`SearchViewModel` no longer holds the whole vault in memory. It keeps only a `NoteFacetRow` projection (no titles, no bodies) to build the filter catalog, the blank-state quick counts, and the file-name match pass above, and loads full rows per search, scoped to the candidates. The Agenda screen and the ledger widget likewise read only rows that actually have a SCHEDULED or DEADLINE, through the body-less `PlannedNoteRow` projection (`toNoteMeta` maps it to `NoteMeta` exactly as it does a full `NoteEntity`); the planning-dates calendar reads a still-narrower `plannedTimestamps()` — just the distinct date strings. `NoteMeta` lazily caches its parsed scheduled/deadline/closed/created dates; sorting and the agenda view use those instead of re-running the timestamp regex per comparison.

## Agenda (`ui/agenda/`)

`AgendaBuckets` owns the day model, deliberately as a pure object (no Android, no ViewModel) so the rules are JVM-testable: `AgendaViewModel` only wires settings and the index flow into it and maps the resulting buckets to rows. The model is stricter than the search one: **an item belongs to exactly one day (its SCHEDULED date if it has one, otherwise its DEADLINE).** That is what makes the "Group by · Date" sections disjoint. A heading with both dates appears once, on its scheduled day, carrying a red `⚑ <date>` chip that announces the deadline. "Overdue" follows the same rule: it is that one date being in the past, not either date being in the past. This replaced `QueryMatcher.agenda`, which bucketed a note under every day either of its dates touched. **Bare active timestamps are the deliberate exception**: a heading with N event stamps produces N agenda entries (one per date, a range expanded to every day it spans), Emacs-style, and an event never shows as overdue once its day has passed. They render a violet `●` chip and weave into the Date grouping only.

The "Show" lever is `Open` · one chip per configured todo-type keyword · `Everything`. The middle chips come from `GroveApplication.keywords`, so the filter follows whatever `todoKeywords` is set to rather than assuming `NEXT`/`WAITING`; `Open` is state-agnostic (anything not done-type, headings with no keyword included). A persisted keyword filter whose keyword has since been removed from the config falls back to `Open` rather than silently matching nothing.

The levers (grouping, state filter, tags/source-file on rows) persist in `SettingsRepository` so they survive a cold start; the Today/Upcoming tab is navigational and resets each visit.

Agenda is also a mutation surface, not just a view: the row checkbox toggles done for a task (`OrgMutations.markDone` / `reopen`) or advances the date for a keyword-less repeating event (`OrgMutations.advanceRepeatingPlanning` / `advanceActiveTimestamp`, via `AgendaViewModel.advanceRepeater`), swipe gestures write planning dates, and the overdue card's "Move to today" rewrites every overdue heading at once. That last one edits several files, so the undo snapshot is a *list* of pre-mutation file texts rather than a single one. Within a file, headings are rewritten highest-line-first and the document re-parsed between edits, since adding a planning line shifts every line index below it. See [tasks-and-events.md](tasks-and-events.md) for the full matrix of which headings get this affordance and what it does.

## Home-screen widgets (`widget/`)

Two Glance (`androidx.glance.appwidget`, 1.2.0) widgets, both RemoteViews under
the hood so they render outside the app's own process/lifecycle. Glance is held
at 1.2.0 or newer deliberately: 1.1.1 had a defect where an app with more than
one widget could cross-wire their generated layouts under update churn and render
one widget's content in the other's slot (the Capture widget redrawing as the
Agenda ledger, or the reverse).

- **Capture** (`CaptureWidget`/`CaptureWidgetReceiver`): one tap, opens the
  capture picker via the `bloom://capture` deep link. No state of its own. The
  asterisk mark is `Image(ImageProvider(R.drawable.ic_brand_asterisk))`, a
  vector reproducing `BrandMark.drawAsterisk`'s five-spoke geometry — not a
  `"✱"` text glyph, which U+2731 renders as blank/tofu on devices whose system
  font lacks it.
- **Agenda ledger** (`LedgerWidget`/`LedgerWidgetReceiver`): the "Widget A ·
  ledger" prototype variant, re-grouped by day (`LedgerBuckets`, pure/JVM-tested
  like `AgendaBuckets`) instead of priority — an always-first unbounded Overdue
  section, then one section per day out to a 14-day window, empty days omitted.
  Row construction is shared with the Agenda screen (`AgendaViewModel.row`), so
  meta chips/tags/priority match exactly. See `../internal-docs/DESIGN_SYSTEM.md`'s "Ledger
  widget" entry for the full visual spec and the Glance-platform limits it runs
  into (no border modifier, no backdrop blur, no real text-layout metrics —
  the checkbox/keyword-pill vertical centering against just the title's first
  line is a fixed-height-box approximation, not a measured one). The header's
  icon tile is the actual theme-synced app icon: `AppIconManager.mipmapRes`
  (new, alongside the existing `markColor`/`targetAlias` per-theme maps) picks
  the same per-theme adaptive-icon mipmap "Sync App Icon with Theme" swaps the
  launcher to.

  `provideGlance` collects the settings and index Flows **inside**
  `provideContent`'s composition (`collectAsState`, seeded with a `first()` read
  so the first frame after a cold session start is already correct). That
  placement is load-bearing, not stylistic: while a Glance session is alive,
  `updateAll()` only *recomposes* the existing content — it never re-invokes
  `provideGlance`. An earlier version read the index into local variables before
  `provideContent` and relied on `updateAll()` to refresh; because recomposition
  replayed the same captured snapshot, the ledger redrew identical rows forever
  and only a brand-new session (app relaunch, host rebind) ever showed an edit.
  That is what made widget mark-done look like a no-op even though the `.org`
  write and the Room reindex had both succeeded. Hoisting these reads back out
  of the composition will silently reintroduce that bug.

  Because the Flows are collected in-composition, any vault write that reaches
  Room now pushes the widget an update on its own. The explicit
  `LedgerWidget().updateAll(context)` calls — from the row checkbox's
  `MarkDoneAction` (an `ActionCallback`, same "mark done" semantics as
  `AgendaViewModel.toggleDone` — recurring headings advance their repeater
  instead of gaining a done keyword and are therefore never auto-archived; a
  non-recurring done item is auto-archived when Settings has it enabled — but
  with no undo), the quick-add composer's send action, and `SyncManager`'s
  `onSyncCompleted` hook — are kept as a nudge for the case where *no* session
  is running, which is the one situation where `updateAll()` does start one and
  re-run `provideGlance`. Tapping a row's body opens Read mode via the same
  `bloom://note/{id}?mode=read` deep link the rest of the app uses (`NoteRef` +
  `Routes.encode`).

  `MarkDoneAction` logs a warning under the `GroveWidget` tag at each of its
  early-return guards (vault never loaded, file missing, no headline at the
  indexed line, no done keyword configured). Those bails are individually
  legitimate but were previously silent, which is what made this class of bug
  so hard to tell apart from "the tap never fired at all".

  Glance dispatches the tap by resolving the callback's *class name* out of the
  intent and calling `getDeclaredConstructor().newInstance()`. Glance's consumer
  ProGuard rule keeps `ActionCallback` implementations as classes but says
  nothing about their members, so R8 shrinks the no-arg constructor away as
  unreachable and the reflection throws — the class ships, the tap does nothing,
  and none of the guard logs above ever run. `app/proguard-rules.pro` therefore
  keeps `<init>()` on every `ActionCallback`. This failure mode is release-only
  (debug builds don't run R8), so a widget action that works from Android Studio
  can still be inert in a production build of the same commit; any new
  `ActionCallback` is covered by the existing rule, but verify a release build,
  not just a debug one.

  The "+" button opens `WidgetQuickAddActivity`, not the full Capture Picker:
  a small transient overlay on the same one-shot-errand pattern as
  `ui/reminders/RescheduleActivity` (empty `taskAffinity`, transparent window,
  excluded from recents), reproducing the prototype's compact `wCapOpen`
  composer instead of the multi-step template flow. The text field auto-focuses
  and shows the keyboard immediately; since a translucent activity's
  `windowSoftInputMode="adjustResize"` doesn't reliably resize the window, the
  activity instead calls `WindowCompat.setDecorFitsSystemWindows(window, false)`
  and the sheet rides the IME inset itself via `Modifier.imePadding()`. The
  target is fixed, not picked per capture: `QuickAddTarget.from(settings)`
  reads Settings § Widget's "Quick add target" (`quickAddTargetFile` +
  '/'-separated `quickAddHeadingPath`, set through the same `RefileSheet`
  drill-down as the archive location; `AppViewModel`'s location picker carries
  a `LocationPickerPurpose` to know which setting a pick saves to). While
  `quickAddTargetFile` is null it falls back to Settings § Sharing's "Shared
  content target", resolved like `AppViewModel.consumeSharedContent` does, so
  updating never moves anyone's tasks. The composer shows the target as a
  plain label (a per-capture file menu didn't scale to vaults with hundreds of
  files). Sending inserts via `CaptureInserter.insertUnderPath` (last child of
  the heading, or bottom of the file for an empty path) +
  `OrgMutations.setPriority`/`setScheduled`, the same on-disk formatting path
  every other capture surface writes through. A heading path that no longer
  resolves falls back to the bottom of the file and a long toast says so,
  rather than creating headings or dropping the typed task.

## Reminders (`reminders/`)

A system notification fires when a heading's SCHEDULED, DEADLINE, or bare active timestamp arrives. Whether it's worded as a task ("due now") or an event ("starting now"), and which actions it carries, is decided purely by `ReminderEntity.isTask` — true only when the heading carries a live TODO keyword, independent of which timestamp field triggered the reminder. Tapping the notification body instead deep-links into the app (`bloom://reminder/...` → `ReminderResolveScreen` → the note in read mode).

A task reminder always carries both **Complete** (flips the TODO keyword to the first done-type keyword via `OrgMutations.changeKeyword`/`markDone`, advancing the date instead when the tracked timestamp has a repeater) and **Reschedule** (opens `PlanningDatesScreen`, focused on whichever date the reminder was for). An event reminder carries only **Reschedule** unless its own timestamp has a repeater cookie, in which case it also gets **Complete** — which advances just that timestamp (`OrgMutations.advanceActiveTimestamp` for a bare active stamp; `markDone`'s repeater path for SCHEDULED/DEADLINE) without touching any keyword, since there isn't one.

Bare active timestamps also arm reminders (`PlanningType.ACTIVE`). A heading isn't unique per stamp, so their `ReminderKeys.reminderKey` takes a `discriminator` (the stamp's ISO date); a range reminds on its start date only. A date-only reminder (task or event) only feeds the digest unless "Notify for tasks without a time" is on (below). `ReminderDigest.count` counts each row on its own day and never as overdue.

- **Identity without file mutation.** A heading is tracked by a best-effort composite key (file name + ancestor-title path + own title + level) rather than an injected `CUSTOM_ID`: renaming or moving a heading can drop tracking for that one reminder, an accepted trade-off in exchange for never writing an ID property the user didn't ask for.
- **Pure core, thin Android shell.** `ReminderKeys` (key/notification-id derivation), `ReminderPlanning` (which reminders a parsed `OrgDocument` implies, and `triggerAtMillis` from a timestamp + the "Default reminder time" setting for date-only stamps; also stamps `ReminderEntity.firesOwnNotification`, true when the stamp has a time-of-day or the "Notify for tasks without a time" setting is on), `ReminderDiff` (schedule/cancel/unchanged diffing against previously stored reminders — a reminder whose `firesOwnNotification`, `isTask`, or `hasRepeater` flipped is re-scheduled even when its trigger time didn't move, since those are read straight off the row at notification time), and `ReminderDigest` (the daily digest count) are plain Kotlin, unit-tested like the rest of the core. `AlarmScheduler` (exact alarm via `setExactAndAllowWhileIdle`, falling back to inexact scheduling when exact-alarm access isn't granted or is revoked mid-flight), `ReminderNotification` (channel, actions, the `bloom://reminder/...` deep-link URI, and the digest notification), and `ReminderReconciler` (ties diffing to Room + `AlarmManager`) are the Android-facing layer.
- **Reconciliation hooks into indexing, not a separate scan.** `RoomNoteIndex.indexNotebook` calls back per file right after it's parsed, and `SyncManager` exposes `onNotebookIndexed`/`onSyncCompleted`, so reminders for an already-parsed notebook go live without waiting on the rest of the vault, consistent with the cold-open fix that decoupled instant file listing from background parsing. `onSyncCompleted` carries the pass's `SyncResult?`; on a successful pass `ReminderReconciler.pruneRemovedFiles` cancels the alarms and drops the rows for any reminder whose file has left the `notebooks` index (deleted or renamed away), and the same sweep runs on app start. A null result (failed sync, or a targeted single-file reindex) skips the prune so a transient failure that leaves the index empty can't cancel live reminders.
- **Daily digest instead of a flood of date-only pings (opt-out per-task).** A heading's SCHEDULED/DEADLINE stamp with no time-of-day falls back to the "Default reminder time" setting for its `triggerAtMillis` (`ReminderPlanning`), and by default shows no notification of its own when that alarm fires (`ReminderAlarmReceiver`/`ReminderReconciler.notify` both check `firesOwnNotification` first). Instead, `ReminderDigestScheduler` arms one independent, self-rescheduling `AlarmManager` alarm at the default reminder time; `ReminderDigestReceiver` fires it, computes `ReminderDigest.count` (overdue + scheduled-today + deadline-today, summed across *every* reminder regardless of `firesOwnNotification`, so a task that also pings individually is still counted here), and shows one "You have X tasks due today" notification (skipped entirely when X is 0) that deep-links to `bloom://agenda`. Turning on Settings → Reminders → "Notify for tasks without a time" flips `firesOwnNotification` for those date-only rows so each one also fires its own notification at the default reminder time (the digest keeps firing independently). Explicit-time reminders are unaffected and keep firing individually at their own time.
- **Four receivers**, each holding `goAsync()` for the duration of its work since a `BroadcastReceiver`'s process can be killed the moment `onReceive` returns: `ReminderAlarmReceiver` (shows the notification when an alarm fires, unless the reminder is date-only and not opted in; first checks the file still exists in the vault, deleting the row and showing nothing if it was removed since the alarm was armed), `ReminderDigestReceiver` (the daily digest, above), `ReminderActionReceiver` (headless Complete: loads the file from the vault, mutates via `OrgMutations`, saves, triggers a sync; only clears the notification/alarm/row after a *confirmed* successful save, never on a best-effort attempt), `ReminderBootReceiver` (re-arms stored alarms and the digest alarm, and fires any per-heading reminders that are overdue-and-unfired, filtering out reminders that already fired so a reboot doesn't re-notify for something the user already saw and dismissed). It also receives `ACTION_SCHEDULE_EXACT_ALARM_PERMISSION_STATE_CHANGED` (API 31+, sent on a grant) and hands it to `ExactAlarmAccessWatcher` (below).
- **Contextual permissions.** `POST_NOTIFICATIONS` and exact-alarm access are requested only when the first reminder actually needs scheduling, via a dismissible `ReminderPermissionBanner` (shown on Notebooks for reminders pending notification access) and Settings › Reminders' `ReminderAccessRows` (at most one row, shown only while access is off and reminders are on: Notifications first, then Exact timing once notifications are allowed, since with notifications off nothing is armed; live-read on every resume rather than inferred from pending rows, since an alarm armed without exact access is never marked pending) rather than proactively at launch; reconciliation always computes and persists what *should* be scheduled regardless of permission state, and arms the actual `AlarmManager` calls once granted.
- **Exact-alarm access changes re-arm alarms.** `AlarmScheduler` picks exact vs inexact only at arm time, so `ExactAlarmAccessWatcher` compares `canScheduleExactAlarms()` with a persisted last-known value (device-local, not exported) on app start, on every return to the foreground, and on the grant broadcast. On a difference it calls `ReminderReconciler.rearmFuture()` (only armed, still-future rows, so it never notifies) and re-arms the digest. This upgrades alarms to exact after a grant, and restores them after a revoke, where Android stops the app and cancels its exact alarms. A missing last-known value (first run after install or update) counts as a change.
- **One-time exact-alarm prompt.** `ExactAlarmPromptDialog` asks for exact-alarm access once, checked on every resume from `GroveNavigation` via `AppViewModel.checkExactAlarmPrompt()`. The decision is the pure `ExactAlarmPrompt.shouldShow`; it requires notifications to be on, since with them off nothing is armed and exact access would do nothing. Either answer sets a device-local `exactAlarmPromptHandled` flag (not exported), after which Settings › Reminders' Exact timing row is the only way back. It never stacks with What's New: the check reruns when that dialog closes.
- **Reschedule is an errand, not a destination.** "Reschedule" starts `ui/reminders/RescheduleActivity`, a second activity with an empty `taskAffinity` (its own task, excluded from recents, transparent window) rather than a route inside `MainActivity`. The user reached the shade from some other app, so confirming a date finishes this activity and drops them straight back into that app; Bloom's own task is neither launched nor disturbed. The write is headless in the same sense as `ReminderActionReceiver` (re-read the file, re-locate the heading by its composite key, `OrgMutations.setPlanningAndActiveTimestamps`, save, request a sync) and runs on `GroveApplication.appScope` so finishing the window the instant the user taps Apply cannot cancel a write still in flight. The reminder row and alarm are left for `ReminderReconciler` to re-derive from the re-indexed file.

## UI (`ui/`)

Jetpack Compose throughout; no XML layouts and no WebViews.

- **Navigation**: a single `NavHost` (`Routes`) with `ModalNavigationDrawer`; deep links for `bloom://note/{id}` and `bloom://capture`, built by `ui/nav/DeepLinks`; every destination also accepts the pre-rename `grove://` scheme as a permanent alias so old pinned shortcuts and automations keep working. A note is addressed by `NoteRef` = `"path/to/file.org@headlineLineIndex"` (optionally `#customId`; the file part is the vault-relative path; `NoteRef.decode` splits on the last `@`, and `Routes.encode` percent-encodes the `/`s), so a ref names any heading in any file. A file's preamble (everything before its first heading) has no headline to key off of. It splits into three independently editable regions: the file-level property drawer, the **preface** (the `#+KEY:` lines) and the **intro** (the free text between them and the first heading). The preface **editor** gets its own route, `preface/{fileName}` (`Routes.preface`). The intro's **read view** rides the normal `note/{id}` route with a sentinel `NoteRef.lineIndex == INTRO_LINE_INDEX` (`-1`, `NoteRef.isIntro` / `NoteRef.intro(file)`), which also flows unchanged through search results and the index (one FTS row per intro, keyed at `-1`); its editor is rendered in place of that route's edit mode rather than getting a route of its own. A single metadata **drawer** (file-level `:PROPERTIES:`, or a heading's `:PROPERTIES:` / `:LOGBOOK:`) is editable in isolation through `drawer/{fileName}?kind={kind}&noteId={noteId}` (`Routes.drawer`), which renders the same editor screen. A single `#+BEGIN_x … #+END_x` **block** in a note body is likewise editable through `block/{fileName}?line={line}` (`Routes.block`), keyed by the block's doc line.
- **Configuration changes**: `.MainActivity` declares a full `android:configChanges` set (orientation, screen size, `uiMode`, `density`, `fontScale`, `locale`, …), so a rotation or a system dark-mode / font-scale change never recreates the Activity. Compose re-reads `LocalConfiguration` / `LocalDensity` and re-lays-out in place, which keeps every screen's in-progress state (an unsaved editor buffer, a half-filled capture, an in-progress date edit, scroll positions) alive across the change. This is safe only because the app is Compose-only with a DataStore-driven theme — nothing reads a `Configuration` field outside Compose or relies on recreation to apply a change. It does **not** cover process death; editor/capture buffers are not yet persisted to `SavedStateHandle` (see `internal/rotation-state-loss-audit-2026-09-01.md`).
- **Org link resolution**: tapping a link in Read mode routes through `DocumentViewModel.openOrgLink`. `OrgLinkParser` (pure, JVM-tested) classifies the target between `[[ ]]` — `id:`, `#custom-id`, `*Heading`, `file:` / bare-path (with an optional `::*heading` / `::#id` search option, resolved relative to the linking file's directory), `denote:` (a Denote identifier, with the same optional search option), an external scheme, or an unqualified "fuzzy" string. The ViewModel then resolves it against the live `OrgDocument`, the Room index (`notes.orgId` / `notes.customId` for a heading, `notebooks.orgId` for a file-level `:ID:` — all three columns indexed, so cross-file `id:` / `#custom-id` links land in O(log n) without opening every file), and `Vault.open` for a cross-file heading match. An `id:` target resolves to a heading anywhere in the vault, or — when it matches a file's leading-property-drawer `:ID:` (`OrgDocument.fileId`, or `notebooks.orgId` across files) — to that file's outline. A `#custom-id` target resolves to a heading anywhere in the vault; a `denote:` target resolves to the notebook anywhere in the vault whose file name carries that identifier (`denoteIdentifier` / `matchDenoteNotebook` in `Vault.kt`: the leading component of `ID==SIG--TITLE__KW.org`, or the `@@`-marked one when components are reordered; a duplicate prefers the linking file's directory) and then behaves like a `file:` target; a `*Heading` and a no-scheme `[[Heading]]` target only ever match a heading title in the current file. A matched heading opens Read mode (`onOpenNote`). A whole-file target opens that file's outline (`onOpenOutline`); a `file:x.org::#id` / `::*heading` target opens that heading's Read mode, falling back to the file's outline if only the in-file heading is missing; an external scheme is handed to the OS; anything unresolved shows a `GroveToast`. The **other direction** — building a link — is the note editor toolbar's link button (`ui/editor/LinkEditing.kt`, pure + JVM-tested, its output round-tripped back through `OrgLinkParser`): with text selected and a URL already on the clipboard, a tap inserts the finished `[[<clipboard-url>][<selection>]]` with nothing to type (the Emacs `org-insert-link` behaviour of picking a URL out of the kill ring; `applyToolbarLink` in `LinkClipboard.kt` reads the clipboard only when text is selected, so the OS paste toast fires only on a real link action); otherwise a tap inserts a `https://` URL scaffold (or the neutral `[[link][description]]` template when nothing is selected), and a long-press opens a file / heading picker in the `RefileSheet` drill-down. A file picked at its top level emits `[[file:rel/path.org]]`; a heading emits a bare `[[*Heading]]` / `[[#custom-id]]` / `[[id:uuid]]` for the current file or a `file:`-qualified form (path relative to the editing file) for another. When the picked file carries a file-level `:ID:`, or the picked heading an `:ID:` / `:CUSTOM_ID:`, a dialog offers the resilient id link in place of the plain one.
- **Deep-link intent as a one-shot**: `bloom://` links (shortcuts, widget, notification) arrive as `MainActivity`'s launch Intent (cold start) or via `onNewIntent` (warm). `MainActivity` threads it to `GroveApp` as Compose state; `GroveNavigation` hands it to `NavController.handleDeepLink` once and then calls `onDeepLinkConsumed(intent)`, which nulls the state and `setIntent(Intent())`. The launch Intent is only read when `savedInstanceState == null`. Together this stops a recreation (process death, or an uncovered config change) from re-dispatching a deep link the user already dismissed — e.g. reopening a cancelled capture sheet. The callback carries the exact Intent and is ignored unless it is still current, so an `onNewIntent` racing an in-flight resolve isn't lost. The `bloom://capture` destination is a `ModalBottomSheet`; its `onDismiss` pops the back stack, and a fast double back-press could fire that callback twice (once from the sheet, once from the system back dispatcher). On the widget's shallow deep-link back stack that popped past the start destination and left the `NavHost` with nothing to render (a blank screen), so `onDismiss` is guarded by `NavBackStackEntry.isResumed()` — a popped entry drops below `RESUMED`, so the second callback no-ops.
- **State**: ViewModels expose `StateFlow`s assembled with `combine` from the vault, the Room index, the sync manager, and settings. Screens collect with `collectAsStateWithLifecycle()`, so collection (and the upstream combine work) pauses while the app is backgrounded. Fast-ticking inputs (per-file sync progress) are combined downstream of the expensive list mapping/sorting, which sits behind `distinctUntilChanged`. `GroveApplication` is the composition root: manual DI, app-scoped singletons wired with flows (e.g. changing the vault folder swaps the `FileStore`, which re-attaches the sync engine; changing TODO keywords clears and rebuilds the index).
- **Compose stability**: the list-bearing UI state classes (`SearchUiState`, `AgendaUiState`, `EditorUiState`, and their nested holders) use `kotlinx.collections.immutable` `ImmutableList` fields rather than plain `List`, and small value holders are `@Immutable`, so a screen re-collecting an unchanged state can skip recomposition. Domain value types the compiler can't verify (`OrgKeywords`, `OrgTimestamp`, `ArchiveTarget`, `java.time.*`) are declared stable in `app/compose_stability.conf`.
- **Editor**: a `BasicTextField` with `OrgVisualTransformation`, highlight-only spans with `OffsetMapping.Identity`, so the text is never altered and cursor math stays trivial. Highlighting is memoized per line content, so a keystroke re-tokenizes only the edited line rather than the whole buffer. `EditNoteScreen` edits one note's subtree, not the whole file; saving splices the subtree back via `OrgMutations.replaceSubtree`, guarded by a revision check (stale-file banner → Overwrite or Reload). A FAB-created note opens with a blank body line appended and the caret placed per Settings § Notes' **New note cursor** lever (`GroveSettings.newNoteCursor`): on that body line (`BODY`, the default) or just past the heading's `* ` (`HEADING`, via `LineEditing.newNoteCaret`, which inserts the space if the stars lack one). `EditRegionScreen` is the same pattern scoped to one region of a file instead of a subtree (`EditorViewModel.loadRegion` / `EditorUiState.region`): a smaller sibling with no heading, so no Read/Edit toggle or metadata sheet. Every region is a line range spliced back with `OrgMutations.replaceLines`, recomputed from the fresh file on save: `INTRO` via `OrgMutations.introRange`, `PREFACE` via `prefaceRange`, the three drawer regions (`FILE_PROPERTIES`, `HEADING_PROPERTIES`, `HEADING_LOGBOOK`) via `fileDrawerRange` / `headingDrawerRange`, and `BLOCK` (a `#+BEGIN_x … #+END_x` body block, markers and folded affiliated lines included — or a standalone `#+KEYWORD:` run) via `blockRange`. The ranges are disjoint and exclude trailing blank lines, so editing one region never disturbs another or the blank line separating them. It opens via double-tapping the matching `CollapsibleKvSection` / `CollapsibleLogSection` / `CollapsibleBlockSection` (`doubleTapToEdit`, same gesture and timing as double-tapping any other note text into edit mode). `EditPrefaceScreen` and `EditIntroScreen` are thin wrappers for their regions. `WHOLE_FILE` is the degenerate region: `loadRegion` hands the editor the entire file text and the save writes the buffer back verbatim (no range to re-resolve, no splice). It backs the whole-file view (`Routes.FILE`, `file/{fileName}?mode=`): `ReadFileScreen` renders the file drawer, preface, intro and every heading in one `LazyColumn` through the same `ReadHeadingRow` note Read mode uses (extracted from `NoteContent`; `relLevel` is the heading's absolute level there), and its Read/Edit toggle switches to `EditRegionScreen` with `WHOLE_FILE` and an `onSwitchToRead`. Neither the toggle nor Back saves: the `file/{fileName}` route hoists the `EditorViewModel` like the note route and hands `ReadFileScreen` a `PendingEdit(wholeFile = true)`, so Read renders the unsaved buffer and leaving Read asks to save (`UnsavedNoteDialog`); re-entering Edit skips the reload (`resumedDirty`). Because that editor is still a single `BasicTextField`, the view is gated on the file's line count: `WHOLE_FILE_LINE_LIMIT` (`ui/vault/WholeFileLimit.kt`, 1000, with a debug-only in-memory override on Settings › Developer) disables the Outline's "View file" item above it. Settings § Roam Features' `roamOpenWholeFile` adds auto-open: `Routes.outline(…, autoOpen = true)` is used wherever the notebook itself is being opened (Notebooks list, `[[file:]]` links, search file matches, an opened `.org` intent); `OutlineScreen` then renders nothing while loading and, once the document fits under the limit, fires `onAutoOpenWholeFile`, which replaces the outline entry with `Routes.FILE` in the default note mode. Breadcrumbs and the file view's own filename tap navigate without `auto`, so they always reach the outline.
- **Roam Features gate**: Roam Features are debug-only. `SettingsRepository` loads `roamFeaturesEnabled` as `BuildConfig.DEBUG && stored`, so a release build turns off every surface keyed off the master switch (Dailies drawer row, Linked References, suggestion strips, roam node templates) without touching the stored value, and `SettingsScreen` hides the Roam Features row. Every editor with a suggestion strip (note editor, whole-file editor, Dailies, capture) hosts it in one `SuggestionSlot` (`ui/editor/SuggestionSlot.kt`): a fixed-height container reserved whenever the IME is visible, whether or not any provider has chips, so the text never jumps. The slot itself is not a Roam feature; only its current providers are. Both Roam providers (the link strip fed by `loadAutoLinkIndex()`, and the roam-node strip fed by `roamNodeSuggestionTemplates`) are gated on `GroveSettings.roamSuggestionsActive` at the view model, and screens take a matching `roamSuggestionsEnabled` param. Link chips render only while the IME is visible. Preface/drawer region editors have no slot, and in other editors both providers stay quiet while the cursor (or selection start) is in the preface (`isInPreface`, `ui/editor/AutoLinkSuggest.kt`).
- **Linked References loading**: `DocumentViewModel` and `EditorViewModel` share one `LinkedReferencesLoader` (`ui/vault/`), which cancels the previous load on each call and builds breadcrumbs only for files with hits (`IndexDao.headingOutlinesFor`). Screens key the load on the target's (file, line, `:ID:`, title), not the parsed document, so edits don't rescan; whole-file views skip files without a file `:ID:`, where the bar is hidden.
- **Dailies open path**: `DailyNoteScreen` never waits for the day index. `DailyNoteLookup` (process-wide, on `GroveApplication`) resolves one day's file name from the Dailies settings and opens it with a single `Vault.open`; `GroveApp` warms it for today whenever the drawer starts opening, so `DailiesViewModel.select` can return a provisional `DailiesNavState` (plain ±1-day neighbours, no date-picker dots) and the parsed note synchronously. The index (`FileStore.listDir` of the dailies folder) builds in the background and then replaces the provisional state with the real prev/next skipping and picker dots.

  **Auto-save.** Every editor saves 5 s after typing stops. Settings § Notes' **Auto-save notes** toggle (`GroveSettings.autoSaveNotes`, DataStore key `auto_save_notes`, default on) switches that idle timer off in `EditNoteScreen` and `EditRegionScreen` alike, leaving the top-bar save icon and the "Save changes?" leave dialog (`UnsavedNoteDialog`) as the only paths to disk. The capture editor's own 5 s idle write is unaffected: it persists a recoverable draft, not a note. Switching Read ⇄ Edit never writes either way — see Read mode's pending buffer below.
- **Read mode**: a custom `AnnotatedString` renderer over the org AST (`BlockParser`/`InlineTokenizer`); the note subtree renders in a `LazyColumn` (one item per visible child heading) so long notes compose lazily, with document traversals memoized per document and body lines resolved per row. A note whose subtree exceeds `LARGE_SUBTREE_THRESHOLD` (60 headings) opens with its inner headings folded (`defaultReadCollapse` seeds every descendant that has children into the collapsed set), so only the note body + a one-level section list mount; smaller notes open fully expanded. Each foldable heading carries an outline-style disclosure caret; `visibleReadRows` filters out anything nested under a folded ancestor. Text selection is scoped per section (one `SelectionContainer` per rendered heading), the trade-off for letting the subtree virtualize instead of living in one eager `Column`. Org tables render as a grid (`OrgTableView`, fed by the JVM-tested `parseOrgTable`): a pinned, bolded header row (every row above the first `|---|` rule), one shared horizontal scroll so wide tables pan with the header tracking columns, and a body capped at 55% of screen height that scrolls vertically beneath the pinned header; the editor still shows the raw pipe text. File-level `#+` keywords (document preamble), `:PROPERTIES:` drawers and `:LOGBOOK:` drawers render as faded, collapsible monospace sections (`CollapsibleKvSection` / `CollapsibleLogSection`), gated by the "Show preface" / "Show property drawers" Settings toggles. `#+BEGIN_x … #+END_x` body blocks (`BlockParser.OrgBlock.Block`) render the same way (`CollapsibleBlockSection`), headed by the block kind with a `#+BEGIN_SRC` language shown alongside, but open expanded and are always shown. A run of standalone `#+KEYWORD:` lines with no block below it (any `#+word:` that isn't a `#+BEGIN_`/`#+END_` marker: `#+CAPTION:`, `#+NAME:`, `#+ATTR_*`, …) also renders through `CollapsibleBlockSection` as an `OrgBlock.Block` with `keywordRun = true` — labelled `KEYWORDS` for two or more consecutive lines, else the sole keyword's name — but opens collapsed like the metadata drawers; a blank line ends a run, and a run directly above a `#+BEGIN` still folds into that block instead. They never rewrite the `.org` file on their own, but double-tapping anywhere on a body row opens `EditRegionScreen` scoped to that region (`onDoubleTap`): the `#+` keyword run for PREFACE, the single drawer for a `:PROPERTIES:` / `:LOGBOOK:` section, or the whole block (or standalone keyword run) for a `Block` section. The **intro** (real content before the first heading, or the whole body of a file with no headings — an org-roam note) is surfaced separately: the Outline shows a tap-only `IntroRow` above the headings, opening an intro-only Read view (`IntroContent`, reusing `BodyBlocks`; filename-only breadcrumb; no title or subtree), whose Read/Edit toggle opens the intro-only editor. The intro is counted as a note and full-text indexed. Its metadata sheet opens with `headline = null`; a state/priority/tag/date/note chip first calls `DocumentViewModel.withIntroHeading`, which splices a blank `* ` heading above the content (`OrgMutations.wrapIntroInHeading`) in one atomic edit, then applies the change and re-opens the note at that heading. The sheet's **★ Favorite** action is the exception: `DocumentViewModel.toggleIntroFavorite` pins the intro to the nav drawer keyed at `INTRO_LINE_INDEX` with no `:CUSTOM_ID:`, so favoriting a heading-less note never forces a blank heading onto the file.

  **Pending buffer.** The Read/Edit toggle (`ReadEditToggle`, one shared component whose whole body is the tap target) writes nothing on any screen, so read mode has to render whatever the editor holds. The `note/{noteId}` route hoists the `EditorViewModel` (the mode toggle never leaves that back-stack entry, so a dirty buffer survives it) and hands read mode a `PendingEdit(fileName, lineIndex, text)`. `DocumentViewModel.setPendingEdit` stores it; `load` splices it over that subtree (`OrgMutations.replaceSubtree`) before parsing, so the rendered note is the unsaved text. Read mode's own mutations run through one choke point, `DocumentViewModel.saveDoc`: when the mutation left the subtree at `lineIndex` intact (a checkbox tap, a metadata-sheet edit) its new subtree text goes back into the editor's buffer via `EditorViewModel.onBufferChangedExternally` and the file is untouched; when it restructured the file instead (refile, delete, move, auto-archive) the computed text — which already carries the unsaved edits — is written as-is and `onBufferPersistedElsewhere` clears the editor's dirty flag so a later save can't clobber the result. Leaving the note for real (back gesture or the ← arrow, not the toggle) mirrors `EditNoteScreen.leave()`'s own decision tree, now against `editorViewModel` instead of its own local state: a just-created note whose heading is still blank (`isCurrentHeadingBlank`) offers `DiscardBlankHeadingDialog` (Discard deletes the on-disk stub via `deleteSubtree`; Keep Editing drops back into edit mode); any other pending buffer raises `UnsavedNoteDialog`, whose Save path is itself blank-heading-gated (`EmptyHeadingAlertDialog`) the same way `trySave()` gates the editor's own save icon; nothing dirty just leaves. Read mode's top bar carries the editor's green save icon while a pending buffer exists, gated the same way. Re-entering edit mode skips the reload from disk (`resumedDirty`) so the buffer is not thrown away.
- **Theme**: the full design-token palette from `../internal-docs/design/README.md` lives in `GroveColors` (light + dark), exposed as `MaterialTheme.grove` alongside the Material color scheme, including the `syn-*` org syntax tokens and the 6-color heading-star cycle.
- **Launcher icon sync** (`icon/AppIconManager`): "Sync App Icon with Theme" (Settings > Appearance) swaps the launcher icon by enabling exactly one `activity-alias` in `AndroidManifest.xml` (`.IconDefault` or one `.Icon<Theme>` per `ThemePreference`) and disabling the rest via `PackageManager.setComponentEnabledSetting`. Because switching the enabled alias closes the app's task, `GroveApp` defers `AppIconManager.applyIcon` to a lifecycle `ON_STOP` observer: the swap happens invisibly when the app goes to the background (hence the "restart the app" toast on enable). The alias `ComponentName`s are built from the fixed manifest package (`com.rrajath.grove`), not `context.packageName`, since the debug build's `applicationIdSuffix` would otherwise produce nonexistent class names. The drawer header logo (`BrandMark`) follows the same toggle: it stays the default light mark when off, and the active theme when on.

  **Notifications do not follow the toggle**, and can't be made to. `NotificationAppearance.markColor` feeds `setColor`, which is what older shades tint the small icon with, and `retintActive` repaints notifications already sitting in the shade when the theme changes (a notification's color is fixed at post time, so a reminder, which lives up to 72h, and the ongoing capture notification otherwise kept the previous theme's mark). But Android 16+ renders the *app's* icon in the shade instead, resolved from the manifest's `<application android:icon>`. Measured on API 37: the enabled alias, `setColor`, and an overridden `android.appInfo` extra were all ignored in favour of the manifest icon, so the shade shows the default mark regardless of the selected theme. There is no app-side lever for it short of shipping a different manifest icon.

- **"NEW" feature dots** (`ui/newbadge/`): a small config-driven framework for pointing returning users at a newly-shipped feature. Each feature is one `NewFeature(id, since, anchors, destination)` in the `NEW_FEATURES` registry (`NewFeatures.kt`); `since` is the `versionCode` it shipped in, `anchors` are string keys for every navigational element that should carry a dot, `destination` is the one whose viewing retires it. `NewBadgeState.from(GroveSettings)` derives the live set: a feature is active when a baseline is recorded, `since > baseline`, and the id isn't in `seenNewFeatures`. The baseline (`GroveSettings.newBadgeBaseline`, DataStore key `new_badge_baseline`) is seeded once — to `lastSeenChangelogBuild ?: currentBuild` — so a fresh install lands on the current build and shows nothing, while an update carries its older build and dots anything newer. State reaches the UI through `LocalNewBadges` (provided at `GroveNavigation`); a call site renders `NewDot(anchorKey)` (a 7dp accent dot inline beside a label, nothing when inactive) or wraps an icon glyph in `NewDotBadge(anchorKey) { … }` (the same dot corner-mounted top-right, ringed in `c.bg`) — a feature living inside a menu lists the container glyph's anchor (`TOPBAR_MENU`) so that glyph is dotted too. The destination site adds `MarkNewFeatureSeen(anchorKey)`, which writes every matching feature id into `seenNewFeatures` when that screen *leaves* composition (so a dot on the destination itself stays visible for the whole visit) — clearing the dot from the whole trail at once. `newBadgeBaseline` / `seenNewFeatures` are device-specific and excluded from settings export. Debug builds expose Settings › Developer › "Reset New badges" (`resetNewBadges()`: clears the seen set, drops the baseline to 0), plus a "Drill-down file count" field that overrides the folder drill threshold (`FOLDER_DRILL_THRESHOLD`, default 20) in memory via `folderDrillThresholdOverride` — never persisted, resets on restart — so the large-folder drill-down view can be tested without creating 20+ files.

## Threading

All file and database I/O is on `Dispatchers.IO` (the `FileStore` implementations switch internally); parsing and matching are cheap enough for default dispatchers; the UI thread only ever touches state flows. Sync runs are serialized behind a mutex and coalesced through `SyncCoalescer` so concurrent triggers can neither interleave nor pile up into repeated full passes.

## Testing

The JVM unit suite (`app/src/test`) covers the pure core: parser round-trips over golden fixtures, mutations, timestamps, placeholder expansion, capture insertion (incl. datetrees), the sync engine against fake stores/indexes, query parsing/matching, line editing, and vault behavior over `JvmFileStore`. UI and SAF behavior are exercised manually / by instrumented tests.

A four-layer automated suite is being rolled out on top (design: `internal/test-suite-00-overview.md`). **M1 (infra) is in place:** a shared `app/src/testFixtures` source set — consumed by both `test/` and `androidTest/` — holds `FakeFileStore` (in-memory `FileStore` with a logical clock for revision changes), `FakeSettingsRepository` (a `MutableStateFlow`-backed `SettingsSource`), `OrgFixtures` (canonical `.org` sample strings), `TestVaultSeeder`, and `InMemoryGroveDatabase`. `AppDispatchers` (held on `GroveApplication`) bundles the main/io/default dispatchers so a test can substitute one `TestDispatcher`; `SettingsSource` is the narrow read interface VMs depend on for settings reads. Robolectric + Turbine are on the per-push JVM suite (`robolectric.properties` pins SDK 34). **M2 (VM constructor refactor) is in place:** every ViewModel takes its collaborators as explicit constructor parameters — `vault`/`keywords` flows, `GroveDatabase`, `SettingsSource` (or `SettingsRepository` for writers), `SyncTrigger` (the narrow interface `SyncManager` now implements), `AppDispatchers`, and the relevant DataStore repos — instead of the whole `GroveApplication`. Each VM's `companion object { val Factory }` builds that wiring from `GroveApplication` (via the shared `factory { }` helper), so nothing outside the composition root changes; a test constructs the VM directly with fakes. A couple of VMs still take an `Application` purely for Context APIs with no JVM stub (`Toast`, asset streams, `contentResolver`, `startActivity`). **M3 (Robolectric + Turbine integration tests) is in place:** every top-level ViewModel — `EditorViewModel`, `CaptureViewModel`, `AgendaViewModel`, `SearchViewModel`, `AppViewModel`, `NotebooksViewModel`, `DocumentViewModel`, `ConflictViewModel`, `SyncLogViewModel` — has JVM integration tests (`*IntegrationTest`) that drive load → edit → save / query / link-resolution / refile / conflict-resolution flows against a real in-memory `GroveDatabase` and an in-memory `FileStore`, in the existing per-push `testDebugUnitTest` job. Shared helpers: `FakeSyncTrigger` (records the sync side-effects a VM requests), `MainDispatcherRule` (swaps `Dispatchers.Main` for one `StandardTestDispatcher` and hands the VM a matching `AppDispatchers`), `TestVaultSeeder.index` (parses fixture files into index rows via `RoomNoteIndex`, no `SyncManager`), and `TestGroveApplication` (a `GroveApplication` subclass with a no-op `onCreate`, for the tests that need the real app type but not its process-start wiring). `SyncManagerRoundTripTest` covers the wired `SyncManager.requestSync` path end to end (disk → index rows, deletion → rows removed, unchanged revision → no-op, `clearAndResync` full rebuild). A test that stands up a real `SettingsRepository` / `FavoritesRepository` cancels its ViewModel scope in `@After` — the whole unit suite is one JVM and a leaked `SharingStarted.Eagerly` DataStore collector on a dead test scheduler can wedge the process-wide DataStore write actor. `NotebooksViewModel`'s settings re-keying side effects are not asserted for the same reason (the vault + index effects, which land first, are). Still to do: `AppViewModel.consumeSharedContent`, which needs `ShareIntake.consumeShare` refactored to take the vault + `SyncTrigger` explicitly rather than reaching through the live `GroveApplication`. **M4 (Compose UI tests) is in place:** `androidTest/` screen tests for `SearchScreen`, `NotebooksScreen`, `OutlineScreen`, `EditNoteScreen`, `OnboardingScreen`, `ReadNoteScreen`, the capture flow (`CapturePickerSheet` + `CaptureEditorScreen`), and `SettingsAppearanceScreen` host each screen directly (not the nav graph) under `GroveTheme` with a ViewModel built from the same `testFixtures` fakes, asserting through the semantics tree (`testTag` / text / `contentDescription`). `ScreenTestEnv` (`app/src/androidTest/.../ui/support`) is the shared wiring — it now also builds a `CaptureViewModel` off the DataStore-backed `TemplatesRepository`; the DataStore-backed `SearchRepository` / `FavoritesRepository` / `SettingsRepository` and the real `GroveApplication` are taken from the instrumented app. A small test-tag inventory was added across those screens (`org_table`, `read_note_scroll`, plus the earlier `search_*` / `notebook_*` / `outline_*` / `edit_note_*` / `capture_*` tags); `EditNoteScreen` gained an injectable `refileViewModel` parameter. The suite runs each test in its own process via **AndroidX Test Orchestrator** (`testOptions.execution = "ANDROIDX_TEST_ORCHESTRATOR"`, `clearPackageData`) — without it the ~30 test activities sharing one process intermittently crash on a leaked `Choreographer` looper. A stateless-screen slice (`SettingsAppearanceRobolectricTest`) also runs under Robolectric `@GraphicsMode.NATIVE` in the per-push JVM job. These otherwise run on the nightly / manual `ui-tests` CI job (`android-emulator-runner`, API 23 + 36, i.e. minSdk and targetSdk), never per-push. **M5 (Maestro end-to-end journeys) is partly in place:** `.maestro/flows/` holds three YAML journeys — capture → confirm, search → open, edit → save — plus the debug-only vault hook they rely on. `MainActivity` reads two launch-intent extras (`grove_test_direct_vault`, `grove_test_seed`) via `DebugTestVault` (`com.rrajath.grove.debug`, no-op unless `BuildConfig.DEBUG`): the first points `GroveApplication.fileStore` at a plain `JvmFileStore` over an app-owned directory (`<externalFilesDir>/testvault`) through the release-inert `TestVaultHook` and marks onboarding skipped; the second seeds that directory from `.org` fixtures bundled into the debug APK's `assets/fixtures/`. Those fixture files live in `app/src/testFixtures/resources/fixtures/` (also where `OrgFixtures` now reads its bodies from) and are copied into the debug assets by the `copyDebugTestFixtures` Gradle task — one source, every layer. Flows run on the manual `e2e-maestro` CI job (`workflow_dispatch`, API 24 + 36 emulators; Maestro's driver needs API 24+); they have not yet been run on a device. Journey 01 (onboarding + the SAF system picker) is deferred. **M6 (Macrobenchmark + Baseline Profile) is partly in place:** a new `:macrobenchmark` module (`com.android.test`, self-instrumenting) holds `StartupBenchmark` (cold / warm × three compilation modes), `ScrollBenchmark` (`FrameTimingMetric` over the Notebooks and Outline lists), and `BaselineProfileGenerator`. The `androidx.baselineprofile` Gradle plugin on `:app` derives `benchmarkRelease` (minified, profileable — what the benchmarks measure) and `nonMinifiedRelease` (what `generateBaselineProfile` collects from) off `release`. The M5 test-vault hook was generalised from `BuildConfig.DEBUG` to a `BuildConfig.TEST_HOOKS` flag (on for `debug` and the two benchmark variants, off for `release` — where R8 then dead-strips `DebugTestVault` entirely) and grew a `grove_test_vault_size` extra that seeds a large synthetic vault (N notebooks + one 500-heading outline) for the scroll benchmarks. `NotebooksScreen` now calls `ReportDrawnWhen { state is Loaded }` so Macrobenchmark's `timeToFullDisplayMs` measures time-to-content rather than time-to-first-frame. These run on the manual `macrobenchmark` CI job (`workflow_dispatch`, `pixel_6` API 34 emulator); they have not been run on a device and no baseline profile is committed yet.

Compose semantics gotcha the M4 tests hit: a row wrapped in a clickable container (`SwipeCommitRow`, `SwipeRevealRow`) merges its descendants, so a `testTag` on an inner element is only reachable with `useUnmergedTree = true`; assert on the row's visible text instead when you also need to click it. Real coroutine dispatchers are used (not a `TestDispatcher`) — a UI test drives async state through `composeRule.waitUntil { … }`, never `advanceUntilIdle()`.

Note: `GroveDatabase.inMemory` uses `BundledSQLiteDriver`. Its native lib ships for Android only, but the desktop `sqlite-bundled` natives are on the unit-test runtime classpath (`testRuntimeOnly` `sqlite-bundled-jvm`), so the driver — with full FTS5 + the trigram tokenizer — loads under Robolectric too. `inMemory` / `RoomNoteIndex` take an optional query `CoroutineContext`; a JVM test passes its `TestDispatcher` so DAO queries settle under `advanceUntilIdle()` instead of on a real IO thread. A concrete `SettingsRepository` (or `SearchRepository`) is constructed with a `CoroutineScope` over that same dispatcher when a VM needs one.

One device-specific trap worth knowing: Android's ICU regex engine is stricter than the JVM's (e.g. a bare `}` outside a character class throws). Regexes must escape `}`/`]`, and JVM tests will not catch violations; see the comment in `PlaceholderExpander`.
