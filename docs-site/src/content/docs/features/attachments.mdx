Attachments let you keep photos, PDFs and other files next to the note they belong to. Bloom stores them the way Emacs [org-attach](https://orgmode.org/manual/Attachments.html) does: each heading gets its own folder inside your vault, named from the heading's `:ID:` and kept under an attachment folder next to the note (`data/` unless you [change it](#settings)), and the note links to the file with an `[[attachment:...]]` link. Since the files are plain files in your synced folder, Emacs on your laptop sees the same attachments, and attachments you add in Emacs show up in Bloom.

## Attaching a file

In [Edit mode](/features/edit-mode), tap the paperclip on the formatting toolbar. The attach sheet opens with the heading (or file) the cursor is in as the target, shown next to **Attach to**. Pick a source:

- **Camera** takes a new photo. It's greyed out when the device has no camera app.
- **Photos** opens the system photo picker. You can pick up to 20 at once.
- **Files** opens the system file picker for any kind of file, several at a time.

Bloom copies each file into the target's attachment folder and inserts an `[[attachment:<name>]]` link at the cursor, one per line. A progress bar shows while larger files copy. If a file with the same name is already there, the new one gets a number added (`photo-1.jpg`, `photo-2.jpg`, ...).

If the target doesn't have an `:ID:` yet, Bloom adds one to its property drawer the first time you attach, since the folder name comes from it. A heading or file with a `:DIR:` property uses that folder instead, as in Emacs.

A heading you attach files to also gets the `:ATTACH:` tag, like Emacs's `org-attach-auto-tag`, so tag searches and the agenda can find headings with attachments.

### Folders from parent headings

A `:DIR:` (or the older `:ATTACH_DIR:`) also applies to everything below it. A heading without its own `:DIR:` uses the nearest parent's, and failing that the one in the file's property drawer. That `:DIR:` wins over the heading's own `:ID:`, so its files go to the parent's folder and no new `:ID:` is added. An `:ID:` is never inherited: a heading with no `:DIR:` anywhere above it uses its own `:ID:` folder.

When the folder comes from somewhere else, the attach sheet says so under **Attach to**: *Folder from \* Trip* names the parent heading, and *Folder from file settings* means the file's property drawer. This works the same when you edit a single heading, since Bloom checks the whole file, and in the capture editor, where headings in the capture use the `:DIR:` of the place the capture lands.

Emacs only inherits `:DIR:` when it's told to. To make Emacs pick the same folders as Bloom, add this to your config:

```elisp
(setq org-attach-use-inheritance 'selective
      org-use-property-inheritance '("DIR" "ATTACH_DIR"))
```

### Changing :DIR: later

If a heading or file already has attachments and you add, change or remove its `:DIR:` property, Bloom moves the files when you save or leave the editor. A popup tells you where they're going, for example *":DIR: property detected. Attachment(s) will be moved to photos"*. Tap **OK** and the popup shows **Moving…** until the files are in place. Removing `:DIR:` moves the files back to the `:ID:` folder. If another heading still uses the old folder, or the folder also holds your notes (`:DIR: .`), only the files that heading links to move, and they're copied when another heading still needs them. If the new folder already has a file with the same name, an identical file is reused. A different one gets a number added (`photo-1.jpg`) and Bloom updates the link to match.

Headings below the one you edited move along when their folder came from it. Adding a `:DIR:` to a parent moves its children's files into the new folder, changing it moves them to the new folder, and removing it moves each child's files to wherever that child now resolves (another parent's `:DIR:`, the file's, or its own `:ID:` folder). Children with their own `:DIR:` aren't touched. When a child moves to the same folder as the heading you edited, the popup shows just one entry for both; a child going somewhere else gets its own entry with its title. A child left with no `:DIR:` above it and no `:ID:` of its own gets a new `:ID:`, and the popup says *"Inherited :DIR: property removed. An :ID: will be added and attachment(s) moved to …"*.

If you remove the last `:ID:` or `:DIR:` from something that has attachments, the popup says *"Image link broken. Couldn't find :ID: or :DIR: property"*. The files stay where they are, so put the property back to fix the links.

This works in the note editor, the Intro and whole-file editors, the property drawer editors, Dailies and the capture editor. Auto-save never moves files, so a half-typed `:DIR:` is safe. The check runs when you tap Save or leave. Choosing **Discard** when you leave puts the note back the way it was when you opened it or last tapped Save, even if auto-save already wrote your changes.

The paperclip is also there when you edit a file's Intro (the text above its first heading). Files attach to the file itself, using the `:DIR:` or `:ID:` from the file's property drawer (`:DIR:` wins when both are set). If the file has neither, Bloom adds an `:ID:` to the file's property drawer.

### In Dailies and the capture editor

The paperclip is also on the toolbar in [Dailies](/features/dailies) and in the [capture editor](/features/capture). Dailies works the same way as any note.

A capture is new text that lands in the template's target file when you save, so its target works a little differently:

- With the cursor under a heading in the capture, the files attach to that heading. Its new `:ID:` and the links are part of the capture and land in the target file with it.
- With no heading in the capture and a template that adds the text under a heading, the files attach to that heading, with `[[attachment:...]]` links. If it needs an `:ID:`, Bloom adds one to the heading in the target file.
- With no heading in the capture and a template that adds the text to a file, a toast says the files attach to the target file instead. Bloom adds an `:ID:` to the target file if it has none and inserts `[[file:...]]` links relative to it. This needs the target file to exist already.
- A new Roam node capture is the whole new file, so with no heading the files attach to the node's own file, under the `:ID:` the node gets when you save.

The capture editor's Read toggle shows attached images inline, the same as a saved note.

Files are copied as soon as you pick them, not when you save. If you discard the capture with **×**, the confirmation offers **Also delete attachments** (checked by default). Leave it checked and Bloom deletes the files attached during that capture, along with any `:ID:` it added to the target file or heading. Uncheck it to keep them.

The original file is never moved or changed. Photos from **Camera** and **Photos** are resized according to the [Photo size](#settings) setting, and HEIC photos are always saved as JPEG so they display everywhere. Files from **Files** are copied exactly as they are.

Below the source buttons, the sheet lists attachments that already exist. Switch what it shows with **Show attachments in**:

- **This heading**: the current heading's own attachments. Not offered when the cursor is above the first heading.
- **This file**: attachments of every heading in the file, plus the file's own.
- **Vault**: attachments across the whole vault.

Each row has up to three buttons. Long-press any of them to see its name.

- **Insert link at cursor** adds a link to that file. A file from the current heading gets an `[[attachment:...]]` link; a file that belongs to another heading or file gets a `[[file:...]]` link relative to the note you're editing.
- **Open with…** hands the file to another app.
- **Delete** removes the file from the attachment folder after you confirm. Links to it stay in your notes and show as missing. It only appears on files that belong to what you're attaching to, in any view, so you can't break another note's links by accident.

## In Read mode

Attachment links display as the files they point to:

- **Images** (`jpg`, `png`, `gif`, `webp`, `bmp`, `heic`) on a line of their own show inline, with the file name underneath. Tap one to open it full screen, where you can pinch or double-tap to zoom and use **Share** or **Open in…**.
- **Other files** show as a chip with a colored badge for the file type. Tap the chip to open the file in another app. An image link with a description (`[[attachment:photo.jpg][Photo]]`) also shows as a chip.
- A **missing** file (deleted, or not synced to this device yet) shows a placeholder. Tapping it tells you which file can't be found. Files that arrive with a later sync show up without reopening the note.

The same applies to `[[file:...]]` links and plain relative paths that point at a non-`.org` file, so links you made in Emacs with `org-insert-link` work too.

To size one image, put an `#+ATTR_ORG: :width 300` line directly above its link. The [Default image width](#settings) setting covers the rest.

In the [Outline](/features/outline-view) and in [Search](/features/search) results, attachment links in note previews show as small chips instead of raw link text.

## Moving and deleting notes

Attachment folders follow the notes they belong to:

- **Refiling or archiving** a heading to a file in another folder moves its attachment folder along with it.
- **Refiling or archiving** a heading whose attachments are in a folder it gets from a parent heading or the file writes that `:DIR:` onto the heading, adjusted for where it lands (for example `:DIR: ../Notes/photos`), so its links keep working. Nothing is written when the new place uses the same folder anyway, or when nothing in the moved heading links to an attachment. Undo takes the `:DIR:` back off. Emacs doesn't do this, so a refile done in Emacs can leave these links broken.
- **Moving a notebook** to another folder asks whether to move its attachments too (the default) or move only the notebook.
- **Deleting a notebook** offers to delete its attachments as well, checked by default.
- **Deleting a heading** in the Outline offers to delete its attachments, unchecked by default. The heading delete can be undone; deleting the files can't.

An attachment folder that's also used by a note somewhere else is never moved or deleted out from under it. It's copied or kept instead, and the confirmation tells you how many.

Attachment folders (`data/`, or the folder you set in [Settings](#settings)) never show up as notebooks, and sync doesn't scan inside them.

## Settings

  light={settingsLight}
  dark={settingsDark}
  alt="Settings › Attachments with a Preview tag, a Photo size switch (Original, Large, Medium, Small) set to Original, a Default image width switch (Fit column, Fixed) set to Fit column, and an Org-attach compatibility section with an Attachment folder row set to data/"

**Settings › Attachments** has three settings. All are included in [Backup](/features/backup-export-import).

| Setting | Options |
|---|---|
| **Photo size** | **Original** (full resolution), **Large** (long edge 2560 px), **Medium** (1920 px), **Small** (1280 px). Applies to Camera and Photos only. |
| **Default image width** | **Fit column** fills the width of the note. **Fixed** shows a stepper for a set width, 120 to 1200 px in steps of 40. An `#+ATTR_ORG: :width` line overrides it for one image. |
| **Attachment folder** | Where `:ID:` folders go, relative to each note's folder. `data/` by default, like Emacs; set it to match `org-attach-id-dir`, for example `attach/` or `.attach/`. Nested folders (`media/files/`) work. Absolute paths, `..` and `~` aren't allowed. Existing attachments aren't moved: files already in `data/` keep opening, and new ones go to the new folder. |

Images are never shown wider than their own size, and tall images are scaled down to fit on screen.
